2. メイン画面モック（グループ枠 + ドッキング）

タブのクリックで切替。仕切り線（青くなる部分）をドラッグするとペインの大きさが変わる。中身は外部アプリのウィンドウで、枠の上に重ねて同期する。

3. ドッキング操作

ドラッグ中のガイド

Chrome — localhost:5173
↑ ←▣→ ↓

タブ（または Shift + 外部ウィンドウのタイトルバー）を掴んでペインの上に来るとガイドが出る。中央に落とすとタブとして追加、上下左右に落とすとその方向に分割する。青い領域が落とした後の配置。

操作一覧

  • 追加: 外部ウィンドウをガイドへドロップ。またはペインの「+」からピッカーで選ぶ
  • 分割: ガイドの上下左右へドロップ
  • リサイズ: 仕切り線をドラッグ
  • 外す: タブを枠の外へドラッグすると単独ウィンドウに戻る
  • 移動: 枠のタイトルバーをドラッグすると中身ごと動く
  • 最小化: 枠を最小化すると中の全ウィンドウを隠す

4. グループの切替（Waypoint に任せる）

専用のパレットは作らない。グループ枠は通常のトップレベルウィンドウで、タイトルを「[グループ名] アクティブタブのタイトル」にする。こうすれば Waypoint の w コマンドなど既存のウィンドウ切替ツールに 1 件として出る。

ケース挙動
切替ツールで枠を選ぶ枠と中の全ウィンドウを前面に出す
切替ツールでグループ内のウィンドウを直接選ぶそのウィンドウを含むタブをアクティブにし、枠ごと前面に出す
グループ内のウィンドウを切替ツールに出すかQ11 で決める

設定画面のラジオボタンで選ぶ。各ペインのタブバーに適用する。

6. 技術スタックの比較（Q6 への回答）

C# + WPF + Win32（推奨）

  • ドッキングガイド、半透明プレビュー、設定画面などの UI を早く作れる
  • WinEvent フック、DeferWindowPos、DPI 対応は CsWin32 で P/Invoke を自動生成すれば手間が少ない
  • WindowTabs も C# 製で、参考にしやすい
  • 弱み: 常駐時のメモリが 60〜100MB 程度になる見込み（未計測）。WPF は NativeAOT が使えず、配布物が大きい

Rust + windows-rs

  • 常駐時のメモリが小さい（数 MB〜十数 MB 程度の見込み、未計測）。起動が速く、単一 exe で配布できる
  • Win32 API をそのまま扱える
  • 弱み: 半透明オーバーレイ、ドラッグ中のガイド、設定画面などの UI を自前で描くか、UI ライブラリの選定が必要になる。今回はこの UI が多く、開発速度の差が大きい

速度・品質の観点（コメントへの回答）

観点Rust の優位このアプリでの影響
ウィンドウ追従の速さGC 停止がない小さい。追従遅れの主因は、外部プロセスが SetWindowPos を処理して再描画するまでの時間と DWM の合成で、言語の差ではない。.NET の GC 停止はヒープが小さい常駐アプリなら通常 1ms 未満（未計測）
起動・常駐コスト起動が速く、メモリが少ない中。常駐アプリなので気にする人はいる。動作の体感にはほぼ出ない
メモリ安全・堅牢性所有権と型でバグを防ぐ限定的。コードの大半が Win32 呼び出しで、Rust でも unsafe が多くなる。C# も managed なので、メモリ破壊はどちらも起きにくい
クラッシュ時の後始末差なしどちらの言語でも、落ちると外部ウィンドウが位置同期されないまま残る。起動時にレイアウトを復元する処理で対処する
フック DLL の注入ネイティブ DLL を作れる今の設計では不要。WinEvent フック（プロセス外）と低レベルマウスフックで足りる。将来、他プロセスへの注入が必要になれば C# 側に C++ の小さな DLL を足す

結論: 速度・品質で Rust が明確に勝つのは常駐コストだけ。推奨は変えず C# + WPF とする。このアプリの難所は Win32 のウィンドウ追従と、ドッキング用オーバーレイ UI の作り込み。後者を WPF で早く回せる利点の方が大きい。常駐コストを最優先するなら Rust を選ぶ。

7. 決めたいこと

#論点状態 / 選択肢 / 私の推奨
Q1何を解決したいか決定: 散らかったウィンドウの整理。ドッキングで自由にレイアウトする
Q2タブバー配置決定: 設定で A / B / C を切り替える。既定は A
Q3グループの永続化ドッキングではレイアウトを作る手間が大きいので、保存の価値が上がる。推奨: MVP で「レイアウトツリー + 各ペインにどのアプリを入れるかのルール（exe 名・タイトル）」を保存する。起動中のウィンドウを自動で割り当て、無ければペインを空けておく
Q4グループ内の分割表示決定: MVP に含める
Q5複数グループの切替決定: 専用 UI は作らず Waypoint の w コマンドなど既存の切替ツールに任せる（4 章）
Q6技術スタック推奨: C# + WPF + Win32（6 章に速度・品質の比較を追加）。これで良いか
Q7キーボード操作例: Ctrl+Win+←/→ でタブ移動、Ctrl+Win+矢印+Shift でペイン間移動、Ctrl+Win+W でグループから外す
Q8新規外部ウィンドウの埋め込み方式 位置同期（推奨）: 外部ウィンドウは独立したまま、ペインに重ねて追従させる。アプリを壊しにくい。代わりに移動時の追従遅れ、Z オーダーのずれ、Alt+Tab に個別に出る、といった不具合が出やすい。
reparent（SetParent）: 枠の子ウィンドウにする。見た目と挙動は一体化する。UWP や一部の Electron アプリ、DPI が混在する環境、管理者権限のアプリで動かないことが多い。
推奨: 位置同期で作る。切替ツールに個別に出る点の扱いは Q11
Q9最小サイズの衝突決定: (a) アプリの最小サイズより小さくなる位置まで仕切り線を動かせなくする
Q10枠を使わない軽量モード決定: 作らない。枠ありだけにする
Q11新規グループ内のウィンドウを切替ツールに出すか 出す（推奨）: 何もしなくてよい。w コマンドで個別のアプリ名からも探せる。選ぶと 4 章の挙動で枠ごと前面に出す。
隠す: 外部ウィンドウのスタイル（WS_EX_TOOLWINDOW 等）を書き換えてタスクバーと Alt+Tab から消す。一覧はすっきりするが、アプリによっては壊れる。こちらのアプリが落ちたときに元に戻す処理も要る
